# PEVT 外部导入与热重载规范

## 1. 这条路径是什么，不是什么

`PEVT-嵌入注册与ID冲突规范.md` 第 1 节规定的分发模型不变：交给玩家的 `.pevt` 永远是压缩载荷，随模组程序集一起编译分发，游戏不从磁盘上找模组的事件文件。

本文规定的是**作者本机的开发路径**：把 `.pevt` 直接从一个目录读进来，或者由 PolarisTools 在保存时推给正在运行的游戏，好让作者改一行、看一眼，而不必走「保存 → 生成 → 编译 → 重启游戏 → 走到那个事件」这一圈。

因此：

- 外部导入默认关闭，由设置项 `polarisevent` 分组里的「外部导入 .pevt（热重载）」打开。关着的时候既不扫任何目录，也不建任何命名管道。
- 外部导入**不是**分发方式。作者要发布事件，仍然只有嵌入包一条路。
- 外部源不因为「在作者自己的机器上」而少走任何一道静态门。语法、绑定、控制流、`enable cs`、`@` 注册表、运行预算全部照常，诊断编号与嵌入源一致。

## 2. 两个入口，一条落地路径

```text
                    ┌──────────────────────────┐
目录扫描（.pevt）───▶│                          │
                    │  PevtRegistryScanner     │──▶ 完整静态校验 ──▶ /event/<id>.pevt
PolarisTools 推送──▶│  .ApplyExternal(sources) │        （外部层）
                    └──────────────────────────┘
```

两个入口只有「字节从哪来」不同，之后共用同一段逻辑：校验、登记、层级判定、重启策略。这是硬性要求——作者在两条路上必须看到完全一样的行为，否则「目录里能跑、推过去不能跑」这类问题无法排查。

游戏侧的落地点是 `Game/Live/PevtLiveImport`，它只能在 Unity 主线程调用（会改注册表、可能重启当前事件）；命名管道线程经 `PevtLiveImport` 之外的 `PevtLivePump` 排队进主线程。

## 3. 加载流程

外部源没有信封字段（没有格式版本、压缩算法、声明长度、声明哈希、声明 ID），因此嵌入包的第 1–4、6 步在这里无从谈起。剩下的三步是：

1. 字节数不超过 `PevtEmbeddedSourceLimits.MaxUncompressedBytes`，否则 `PEVT9211`。
2. 严格 UTF-8 解码，否则 `PEVT9212`。BOM 在建立外部源时按嵌入包的约定去掉。
3. 用共享语言核心执行完整静态校验，失败时保留语言核心自己的 `PEVTxxxx`，不套包装编号。

事件 ID 只可能来自源码里的 `id`，与文件名无关：`WronglyNamed.pevt` 里写 `id "Real"`，进 `/event` 的就是 `Real`。

失败的文件不进入 `/event`，也不写进 `PevtEventRegistry.Failures`——那张表是「随程序集分发的嵌入包加载失败」，作者本机改坏的一行不该混进去。外部失败留在 `PevtExternalApplyReport` 里，由调试页的 Live 分页与推送回执呈现。

## 4. 来源层级

候选定义带一个来源层级 `PevtEventOrigin`：

| 层级 | 含义 |
| --- | --- |
| `Embedded` | 随模组程序集分发的嵌入包。发布路径只有这一种。 |
| `External` | 作者本机导入的 `.pevt`：目录扫描或热重载推送。 |

派生生效集合分两层：

1. 在嵌入层内部按 `PEVT-嵌入注册与ID冲突规范.md` 第 6 节定胜负（跨程序集重复是致命冲突并保留先注册者，同程序集重复是警告并后注册覆盖先注册）。
2. 外部层同样按第 6 节在层内定胜负（同一个 owner，因此两个外部文件抢同一个 ID 是警告，后者胜），然后整体压到嵌入层之上。

分层而不是把所有候选放进一个序列排序，是为了让两件事互不污染：

- **外部压嵌入不是冲突。** 作者一旦把事件打进程序集，就必须还能在游戏里迭代同一个 ID，否则热重载对已发布的事件完全无效。这种覆盖记为 `PevtEventOverride`，不进 `Conflicts`，也不进 `FatalConflicts`——后者会让 `callevt` 把该 ID 判成歧义目标而拒绝调用。
- **外部导入不得和解掉发布路径上的冲突。** 两个模组抢同一个 ID 仍然是致命冲突并照常上报，不因为作者本机恰好也导入了一个同名事件而消失。

外部候选统一挂在 owner `#external` 名下。`#` 开头不可能是程序集名，因此撤销外部导入永远不会碰到任何模组的注册。

## 5. 整批替换语义

`ApplyExternal` 是**替换**而不是追加：先撤销 `#external` 名下的全部候选，再登记这一批，最后只重新派生一次。

必须如此。热重载的语义是「磁盘上/项目里现在有这些文件」，作者删掉一个 `.pevt` 之后它就该从 `/event` 里消失；逐个追加做不到，只会让上一轮的事件一直赖在表里，而作者以为自己已经删掉了它。同理只派生一次，避免中间态被别人看见。

这也决定了 PolarisTools 推送的粒度：推的是**整个项目的 `.pevt` 快照**，不是刚保存的那一个文件。

撤销外部导入（调试页的按钮、关掉设置项、插件卸载）之后原本被盖住的嵌入版本自动重新生效。

## 6. 目录导入

- 默认目录 `BepInEx/Polaris/pevt/`，打开开关时幂等建出来。
- 设置项可以改成任意目录并展开 `%环境变量%`；作者常直接指向自己的 PolarisTools 工程目录。填了自定义目录时**不**替他创建：那种情况下目录不存在多半是路径打错了或者盘没挂上，建出一个空目录只会掩盖问题。
- 递归扫描 `*.pevt`，跳过路径里含 `bin` 或 `obj` 段的副本——`.pevt` 会作为内容项被拷进输出目录，不跳过的话同一个事件 ID 会以两份路径出现，白撞一条同 owner 重复警告。
- 按完整路径的序数序登记。顺序决定重复 ID 的胜负，随文件系统枚举顺序漂移的话同一个目录两次启动可能跑的不是同一份事件。
- 文件数上限 `PevtLiveProtocol.MaxFiles`；超出时截断并在回执里说明截断了多少，不静默丢弃。
- 读不出来的文件（占用、权限）单独列出，不影响其余文件导入。

可选的文件监视（默认开）在目录里的 `.pevt` 变动后经一段静默期重新导入。静默期是必要的：编辑器保存一次文件会连着触发好几个改动事件，每一个都重扫一遍等于把整个目录解析好几遍，还可能读到只写了一半的文件。监视回调跑在线程池上，只记一个时间戳，重扫由主线程的对账点执行。

## 7. PolarisTools 热重载通道

命名管道，游戏侧服务端，PolarisTools 客户端。协议常量与帧格式的唯一定义在 `Live/PevtLiveProtocol.cs`，它编译进 PolarisEvent 的 netstandard2.0 目标，而 PolarisTools 对那个目标是 `ProjectReference`——两侧不存在各写一份常量然后慢慢分叉的可能。

```text
int    Version          // 不一致时明确报错，不按错误的字节序列硬解
string FocusPath        // 触发本次推送的文件，空串表示没有特定焦点
int    Count
Count × { string SourcePath; string Text }
---- 回执 ----
bool   Ok
string Message
```

- 服务端只在设置项打开时启动。关着的进程上没有任何可连的端点。
- 上限在读取过程中生效，不是读完再判断：对端可以声明十万个文件，先分配再检查等于把内存交给对端决定。
- 触发点是 PolarisTools 的 `.pevt` 单文件生成器跑完之后，而不是保存事件本身。这样「编译进程序集的那一份」和「推给游戏的那一份」出自同一次保存，不会一前一后差一个版本。
- 游戏没开着是常态：连接超时很短，连不上完全静默。不能让每次保存都提示一次「没连上游戏」。
- 工具侧对每个文件做严格 UTF-8 解码并点名失败的那一个。不这么做的话，一份没存成 UTF-8 的文件在游戏侧只会表现为一串莫名的词法错误。

## 8. 重启策略

**正在运行的事件不做就地替换。** 总纲 3.2 已经规定「运行实例固定使用启动时的定义代次，不在事件执行中途替换语法树」，热重载不是这条规则的例外：一个跑到一半的事件已经建立了等待、协程和一整棵所有权树，把它们接到另一份指令流上无法保证语义，只会得到一个既不是旧版也不是新版的状态。

因此策略只有两种，由设置项选择：

- 默认：当前根事件的 ID 恰好在这一批重新导入的事件里时，把它**从头重启**（走 `Change`，旧事件先完整清理）。代价是作者会看到事件回到开头，这是可预期的。
- 关掉：只更新注册表，下一次启动才用到新版本。

重启失败（例如新版本用到了运行时尚未支持的构造）不让整次导入失败：事件已经登记好了，作者改完再存一次即可。

导入时顺手丢掉这些事件 ID 的编译缓存。缓存键带内容哈希，旧版本本来不会被误命中；清掉只是因为作者会把一个事件改上百遍，每一版都在缓存里留一份编译产物是一条只增不减的内存占用。

## 9. 调试页

调试页的 Live 分页是作者判断「我改的那一版到了没有」的唯一去处：

- 生效目录、是否在监视、是否重启当前事件；
- 「重新扫描目录」与「撤销外部导入」两个按钮；
- 命名管道名、协议版本、服务端是否在听、已收到几次推送、最近一次通道错误；
- 最近一次导入的代数、时间、来源，以及逐文件结果——成功的带一个直接启动的按钮，失败的带诊断编号与行列；
- 当前生效的外部事件列表。

Events 分页给外部候选标 `[external]`，并单独列出被外部导入盖住的嵌入事件，两个分页的结论必须一致。

## 10. 与人物目录的关系

`.pactor` 目前没有对应的外部导入路径。外部事件能用的人物是内置 `aic` 目录加各模组已经嵌入注册的目录；改人物目录仍然需要重新编译。

# PEVT 阶段验收与自动探针规范

## 1. 目的

本文规定阶段 10A 之后所有 PEVT 阶段的验收方式，解决“现有测试全绿，但计划要求没有真正实现”的问题。

验收采用失败关闭原则：探针不能证明某项要求已经完成时，该项就是 `FAIL`，不能按“应该已经包含”“结构天然等价”或“后续再处理”推定通过。

本文约束 Claude 自检、人工复核和未来迁移后的 MCP 自动交付探针。它不改变语法和运行语义；冲突时需求真相优先级仍以 `PEVT-Claude分阶段实现计划.md` 为准。

## 2. 阶段状态机

每个阶段只有以下状态：

```text
PLANNED -> IMPLEMENTING -> VERIFYING -> ACCEPTED
                    \-> FAILED <-----/
```

- `PLANNED`：执行合同和验收清单已存在，尚未改代码。
- `IMPLEMENTING`：只允许修改合同列出的范围。
- `VERIFYING`：停止增加功能，只修复本阶段验收失败。
- `ACCEPTED`：所有强制门均通过，证据文件完整，独立复核无阻断项。
- `FAILED`：任意强制门失败。修复后重新进入 `VERIFYING`，不能跳过。

只有 `ACCEPTED` 可以推进阶段游标。测试通过、构建成功、达到行数或 Claude 自己声称完成都不能单独改变游标。

## 3. 每阶段必须存在的执行合同

阶段开工前必须提供一份机器可读合同。未来探针迁移后建议存放为：

```text
doc/design/stages/PEVT-stage-<阶段号>.contract.json
```

最低结构：

```json
{
  "stage": "10A",
  "title": "词法、语法与深不可变补正",
  "planRevision": "计划文档内容哈希",
  "allowedPaths": ["PolarisEvent/Syntax/**", "tests/PolarisEvent.Tests/Syntax/**"],
  "requirements": [
    {
      "id": "10A-R01",
      "text": "文件 ID 拒绝空字符串",
      "spec": ["PEVT-语法设计草案.md#文件头", "PEVT1110"],
      "artifact": "Parser.ParseIdDeclaration/绑定后的等价入口",
      "positiveCases": ["ASCII ID", "中文 ID"],
      "negativeCases": ["空 ID"],
      "forbiddenSubstitutes": ["只在诊断目录登记 PEVT1110"]
    }
  ],
  "diagnosticOwnership": [
    { "id": "PEVT1110", "ownerStage": "10A", "mustEmitNow": true }
  ],
  "publicArtifacts": [],
  "deferred": [],
  "forbidden": []
}
```

合同必须满足：

- 每条要求有稳定 ID，不能用一条要求打包多个无法独立验收的行为；
- 每条要求列出权威规范、产物、正常样例、无效样例、边界样例和禁止替代方案；
- 所有相关诊断都有唯一负责阶段；
- `deferred` 必须同时写出原因、负责阶段和前一阶段需要保留的接口/数据；
- 合同开始实现后不得由实现者静默删除或弱化要求；变更必须记录原因并重新进入 `PLANNED`。

## 4. 每阶段必须生成的证据

Claude 完成实现后必须输出机器可读证据，未来建议放在临时构建目录而不是提交仓库：

```text
artifacts/pevt-stage-<阶段号>.evidence.json
```

每条 requirement 至少包含：

```json
{
  "requirement": "10A-R01",
  "productionEvidence": [
    { "path": "PolarisEvent/Syntax/Parser.Statements.cs", "symbol": "ParseIdDeclaration" }
  ],
  "positiveTests": ["DocumentParserTests.AcceptsAsciiAndChineseId"],
  "negativeTests": ["DocumentParserTests.RejectsEmptyIdWithPevt1110"],
  "adversarialTests": [],
  "status": "PASS"
}
```

探针必须验证路径、符号和测试名确实存在，不能只接受文字声明。没有生产证据、没有反向测试或填写 `N/A` 而未在合同中预先批准时，直接失败。

## 5. 十一道强制验收门

### G0：范围与基线门

- 阶段开始时记录工作树状态、已有测试数量和相关文件哈希；用户原有修改不计入本阶段。
- 变更路径必须落在 `allowedPaths`；越界文件逐个解释，否则失败。
- 禁止 reset、checkout、批量格式化或删除用户修改来制造干净差异。
- 有效变更行数遵守主计划预算，但行数通过不代表功能通过。

### G1：构建与测试门

- 运行主计划和当前接手说明列出的全部 build/test 命令。
- 必须报告测试总数、失败数、跳过数和与阶段开始时的差异。
- 新增跳过、显式忽略、条件屏蔽或删除测试一律失败，除非执行合同预先批准。
- 测试数量下降时必须列出删除的精确测试及用户批准记录。

### G2：逐需求证据门

- 合同中的每条 requirement 必须恰有一个最终 PASS/FAIL。
- PASS 必须同时存在生产代码、正向测试、反向或边界测试。
- “同类测试已经覆盖”“另一个类型也这样做”不能作为证据。
- 公开产物必须能由测试直接观察，不能只在局部变量、临时字典或日志中出现。

### G3：诊断三联覆盖门

对本阶段 `mustEmitNow=true` 的每个 PEVT/PEVTR 编号同时检查：

1. 权威诊断表和 `DiagnosticCatalog` 中登记一致；
2. 生产代码存在实际发射路径，目录定义和注释不算；
3. 测试直接断言该编号，并至少有一个合法邻近样例证明不会误报。

探针输出五列账本：编号、目录、发射点、正向测试、反向测试。任意空列失败。

`mustEmitNow=false` 的编号必须有唯一未来阶段；同一编号出现多个 owner 或没有 owner 都失败。

### G4：公开产物形状门

凡计划使用“生成、产出、保存、解析为、绑定为”的要求，探针必须检查交付模型的实际成员：

- 绑定程序必须真的包含 Bound 节点，不能只保存 SyntaxNode；
- 控制流必须真的包含节点/边/目标，不能只提供遍历器；
- 已解析目标必须保存在结果中，不能分析后丢弃；
- 参数域、Descriptor、注册表和服务接口必须只有一个权威入口；
- 后续阶段不得为了使用该产物重新扫描 token、文本或反射猜测语义。

执行合同必须列出所需类型和成员；反射测试或公开 API 快照逐项核对。缺成员或出现第二套平行模型时失败。

### G5：深不可变与所有权门

所有声称不可变的模型必须执行别名攻击测试：

- 用可变 List/Dictionary/array 构造对象；
- 构造后修改、清空或替换原集合；
- 验证对象内容、哈希、枚举结果和子对象均未变化；
- 验证公开属性不能向外泄漏可写集合；
- 资源/句柄模型还要验证 owner、取消和清理边界。

只有 get-only 属性不算不可变。

### G6：边界与对抗门

每条非平凡要求至少有一个“击穿近似实现”的测试。按领域选取：

- 数值：min、max、刚好越界、负号/括号/双负号；
- 文本：空、中文、其他 Unicode、转义、换行、tab、注释相邻；
- 语句：关键字开头与非关键字开头的同行双语句；
- 控制流：向前/向后/跨环境/进入结构/goto 后重新可达；
- XML：未知元素/属性、DTD、实体、NaN/Infinity、信任伪造；
- 注册：同 owner、跨 owner、相同 ID 不同内容、相同内容不同来源；
- 异步：同帧完成、取消竞态、失败与成功混合、事件结束泄漏；
- 资源：加载中取消、重复借用、owner 卸载、失效引用。

合同没有对抗样例时不能进入 `IMPLEMENTING`。

### G7：延期与可疑说明门

扫描本阶段生产代码和测试中的：

```text
TODO
FIXME
NotImplementedException
留给后续
不在本阶段
天然就是
暂不实现
阶段 N 再处理
```

每处命中必须映射到合同中的 `deferred` 项和唯一 owner。没有映射、owner 是当前或更早阶段、或者文字与计划冲突时失败。

注释不能改变计划范围。若代码注释声称某项无需实现，而计划要求实际产物，按计划失败。

### G8：测试防弱化门

- 探针比较阶段前后测试差异，标记删除断言、扩大允许集合、把 Error 改为 Warning、把精确编号改成“任意诊断”等行为。
- 对每个修复至少运行一次反事实检查：临时屏蔽关键生产分支后，对应新测试必须失败。未来探针可通过一次性隔离 worktree 中的受控补丁或变异测试实现，禁止修改当前用户工作树；无法执行时由独立复核者手工确认测试确实能抓住缺陷。
- 只验证“不抛异常”或“diagnostics 没有错误”的测试不能单独证明具体语义。
- snapshot/golden 更新必须展示差异，禁止无审阅整体覆盖基准文件。

### G9：依赖、旧链与唯一入口门

- 执行旧 `.phxx/.cmd/EvReader` 链扫描；只有主计划明确的 RawCmd 白名单可以命中。
- 检查 `netstandard2.0` 前端依赖不含 Unity、BepInEx、游戏程序集、PolarisCore、PolarisRes 或 VS SDK。
- 检查同一职责没有第二套 parser、Descriptor、ActorCatalog、registry、scheduler、wait 或 plugin loop。
- 新增项目引用必须符合接手说明中的依赖方向。

### G10：独立复核门

实现者自检通过后，必须由一个不继承实现过程结论的独立复核上下文进行反证式验收：

1. 只读取权威规范、阶段合同、最终 diff 和测试结果；
2. 为至少三个核心要求提出可能漏检的反例；
3. 检查生产产物是否只是近似替代；
4. 检查诊断覆盖和延期归属；
5. 输出 `ACCEPT` 或带 requirement ID 的 `REJECT`。

独立复核不得因为实现者解释“以后会做”而放行当前阶段要求。存在 `REJECT` 时游标不推进。

## 6. 探针判定算法

未来 MCP 探针按以下顺序执行，任何一步失败立即保持当前游标：

```text
读取计划与 stage contract
    -> 验证 planRevision，防止按旧计划交付
    -> G0 范围与基线
    -> G1 构建与测试
    -> G2/G3 需求和诊断证据
    -> G4/G5 产物与不可变性
    -> G6/G7 对抗与延期扫描
    -> G8 测试防弱化
    -> G9 依赖和唯一入口
    -> G10 独立复核
    -> 写入 ACCEPTED 和证据哈希
    -> 原子推进游标
```

游标推进必须是最后一步，并绑定以下哈希：

- 主计划版本；
- 阶段合同；
- 验收证据；
- 被验收源文件集合；
- 测试结果摘要。

任一哈希在推进前变化，重新验收。探针崩溃、超时、输出解析失败或证据缺失都按失败处理，不能默认成功。

## 7. 阶段 10A–10D 的额外检测

### 10A

- 自动运行 ID 字符表、int32 边界矩阵和所有语句起始形态的同行双语句矩阵；
- 对全部 Syntax 集合执行别名攻击；
- 语法诊断按 owner 清单逐编号核对。

### 10B

- 反射确认存在独立 Bound 节点和 ConstantValue，而不是 SyntaxNode 类型别名；
- 每个成功绑定表达式都产生可观察 Bound 结果；
- 类型矩阵、错误传播和复制契约逐项测试。

### 10C

- 每个成功调用保存唯一选中 Descriptor、参数绑定和返回契约；
- PEVT7/8 诊断按当前/延期 owner 分账；PEVT8007–8015 只能归阶段 39；
- 未知 callevt ID 必须静态通过，同时其他签名错误仍会失败。

### 10D

- 反射/API 快照确认 ProgramDefinition 同时含 Bound、Flow、源码映射和哈希；
- golden 图必须列出节点索引、边种类和解析目标；
- 直接调用公开构建入口时不能绕过 Bind/Flow；
- 解释器所需跳转信息不得要求重新扫描源码或 AST 猜测。

## 8. 当前落地状态

- 主计划已经要求阶段合同、证据矩阵、反向审计和唯一所有者。
- `CodexDynamicProbe.Mcp` 1.0.0 已迁移到验收标准 v2：支持 `10A–10D` 阶段 ID、计划/合同/证据哈希、G0–G9 自动门和 G10 独立复核。
- 阶段 10A、10B、10C、10D、11 已提供机器可读合同；阶段 12 以后开始前必须先补同格式合同，否则探针失败关闭且不能领取。
- 没有可调用 Claude CLI 时，G10 使用一次性 nonce、源码哈希和证据哈希生成外部审查包，由未参与实现的新会话通过 `pevt_stage_review_submit` 提交；源码或证据变化立即使报告失效。
- 旧验收状态已自动失效，阶段游标固定为 10A；不得以旧探针成功、旧测试数量或自然语言总结替代本文门槛。
